PART 1 — APP & MVP OVERVIEW
================================================================================

App Name: Safepay
Purpose: Escrow-based payment system for online commerce trust
Problem: Buyers can't trust unknown sellers on social commerce / independent sites
Target Users: Customers buying online, Merchants selling online, Admin (planned)
Core Value: Payment locked in escrow → released only after delivery confirmation

MVP Scope:
- Escrow payments via Razorpay
- Delivery confirmation
- Manual dispute resolution
- Merchant payouts
- Customer wallet

Post-MVP:
- AI dispute resolution
- Automation & compliance
- Trust badges
- Social login (Google/Apple)
- OTP verification via SMS
- Advanced analytics

Monetization:
- 2% service fee on customer payments
- 1% merchant payout/withdrawal fee

Platform Scope: Web (mobile-responsive PWA-style) — Customer + Merchant portals
Admin portal: NOT YET BUILT

Primary User Journeys:
1. Customer → Create Payment → Escrow Locked → Merchant Ships → Customer Confirms → Funds Released
2. Customer → Raise Dispute → Admin Reviews → Refund or Release
3. Merchant → View Orders → Add Tracking → Customer Confirms → Withdraw Funds

PART 4 — COMPLETE WORKFLOW MAPPING
================================================================================

WORKFLOW 1: CUSTOMER PAYMENT FLOW
----------------------------------
Trigger: Customer navigates to /payment/new
Steps:
  1. Customer enters merchant ID + amount + description
  2. System validates merchant exists (merchants table SELECT)
  3. Data stored in sessionStorage.pendingPayment
  4. Redirect to /payment/review
  5. Customer reviews breakdown (amount + 2% service fee)
  6. Customer agrees to T&C, clicks "Pay with Razorpay"
  7. System creates order in orders table (status: pending, escrow_status: held)
  8. Edge function razorpay/create-order → creates Razorpay order
  9. payment_transactions record created (status: pending)
  10. Razorpay checkout modal opens in browser
  11a. SUCCESS PATH:
      - razorpay/verify-payment → verifies via Razorpay API
      - payment_transactions updated (status: success)
      - orders.escrow_status confirmed as "held"
      - sessionStorage.paymentSuccess set
      - Navigate to /payment/success
  11b. FAILURE PATH:
      - razorpay/update-failed → marks transaction failed
      - orders updated (status: cancelled, escrow_status: refunded)
      - sessionStorage.paymentStatus set with error
      - Navigate to /payment/status
  11c. CANCEL PATH:
      - User closes Razorpay modal
      - Same as failure path with "User cancelled payment" reason
Data Reads: profiles, merchants (for validation)
Data Writes: orders (insert), payment_transactions (insert/update)
Failure Handling: Toast error, order marked cancelled
Final State: Order in escrow (success) or cancelled (failure)

WORKFLOW 2: MERCHANT TRACKING FLOW
------------------------------------
Trigger: Merchant clicks "Add Tracking" on order detail page
Steps:
  1. Navigate to /merchant-add-tracking/:orderId
  2. Merchant enters tracking number, courier partner, dates
  3. System inserts into order_tracking table
  4. System inserts initial tracking_update
  5. System updates orders.status → "shipped"
  6. Database trigger fires → creates order_event
  7. Database trigger fires → creates notification for customer
  8. Customer sees tracking via real-time subscription at /orders/:id/tracking
  9. Merchant can later edit at /merchant-edit-tracking/:orderId
Data Reads: orders, order_tracking
Data Writes: order_tracking (insert), tracking_updates (insert), orders (update)
Failure Handling: Toast error on insert failure
Final State: Order status "shipped", tracking visible to customer

WORKFLOW 3: DELIVERY CONFIRMATION
-----------------------------------
Trigger: Customer clicks "Confirm Delivery" at /orders/:id/confirm
Steps:
  1. Customer views delivery details
  2. Confirms delivery
  3. orders.status → completed
  4. orders.escrow_status → released
  5. orders.delivered_at → now()
  6. Database triggers fire:
     - order_event created
     - notification sent to customer
  7. Merchant wallet should be credited (NOTE: no automatic credit logic found)
Data Reads: orders
Data Writes: orders (update)
Final State: Order completed, escrow released

WORKFLOW 4: DISPUTE FLOW
--------------------------
Trigger: Customer clicks "Raise Dispute" on order
Steps:
  1. Navigate to /dispute/:orderId
  2. Customer selects issue type, enters reason/description
  3. disputes record inserted (status: open)
  4. Navigate to /dispute/:orderId/upload/:disputeId
  5. Customer uploads evidence files to dispute-files bucket
  6. dispute_files records created
  7. Dispute visible at /disputes/:disputeId
  8. Merchant sees dispute at /merchant-disputes
  9. Merchant responds at /merchant-dispute-response/:disputeId
  10. Merchant uploads counter-evidence at /merchant-dispute-upload/:disputeId
  11. ADMIN RESOLUTION: NOT IMPLEMENTED — no admin can resolve disputes
  12. Result viewable at /disputes/:disputeId/result
Data Reads: orders, disputes, dispute_files, dispute_comments, dispute_updates
Data Writes: disputes (insert), dispute_files (insert), dispute_comments (insert)
Failure Handling: Toast errors
Final State: Dispute open (stuck — no admin to resolve)
CRITICAL GAP: No admin resolution flow exists

WORKFLOW 5: MERCHANT PAYOUT
-----------------------------
Trigger: Merchant clicks "Withdraw" at /merchant-withdraw
Steps:
  1. Merchant must have bank account (/merchant-bank-account)
  2. Enters withdrawal amount
  3. merchant_payouts record inserted (status: processing)
  4. Database trigger process_merchant_payout fires:
     - merchant_wallets.balance -= amount
     - merchant_wallets.pending_balance += amount
  5. On completion (manual/admin):
     - pending_balance -= amount
     - total_withdrawn += amount
  6. On failure:
     - balance += amount (refund)
     - pending_balance -= amount
  7. Navigate to /merchant-withdraw-success
Data Reads: merchant_wallets, merchant_bank_accounts
Data Writes: merchant_payouts (insert), merchant_wallets (update via trigger)
CRITICAL GAP: No mechanism to complete/fail payouts (no admin, no automation)

WORKFLOW 6: AUTHENTICATION LIFECYCLE
--------------------------------------
Login:
  Trigger: User submits phone + password
  1. Edge function auth/login called
  2. Phone normalized, variants generated for lookup
  3. Profile found in profiles table
  4. Password verified (PBKDF2 with salt, or legacy SHA-256)
  5. Session token generated (64 hex chars)
  6. user_sessions record created (expires: 30 days)
  7. Wallet ensured (created if missing)
  8. Token + user data stored in localStorage
  9. AuthContext.user set → isAuthenticated = true

Session Verification:
  Trigger: App load (useEffect in AuthProvider)
  1. Token read from localStorage
  2. auth/verify-session called
  3. Token matched against user_sessions (must not be expired)
  4. If valid → user data refreshed
  5. If invalid → localStorage cleared, user = null

Logout:
  Trigger: User clicks logout
  1. auth/logout called with token
  2. Session deleted from user_sessions
  3. localStorage cleared
  4. user set to null

Password Change:
  Trigger: User at /change-password
  1. auth/change-password called with userId, currentPassword, newPassword, token
  2. Session verified
  3. Current password verified
  4. New password validated (different from old)
  5. Password hash updated (PBKDF2)
  6. All other sessions invalidated
  7. New session created

Account Deletion:
  Trigger: User at /delete-account
  1. auth/delete-account called
  2. Profile and related data deleted

A. DATABASE TABLES (22 tables)
-------------------------------

1. profiles
   Columns: id (uuid PK), phone, password_hash, full_name, email, auth_method,
            account_source, account_claimed, avatar_url, address, city, country,
            last_login_at, created_at, updated_at
   RLS: INSERT (true), SELECT (true — SECURITY RISK), UPDATE (true — SECURITY RISK)
   Note: password_hash is readable by any anon key user

2. user_sessions
   Columns: id (uuid PK), user_id (FK→profiles), token, expires_at, created_at
   RLS: ALL (true)

3. user_roles
   Columns: id (uuid PK), user_id, role (enum: customer/merchant/admin), created_at
   RLS: INSERT (true), SELECT (own only)
   Unique: (user_id, role)

4. orders
   Columns: id (uuid PK), customer_id (FK→profiles), merchant_id (FK→merchants),
            order_number, merchant_name, merchant_avatar, product_name,
            product_description, amount, currency, status, escrow_status,
            expected_delivery, delivered_at, notes, created_at, updated_at
   RLS: INSERT (true), SELECT (customer own + merchant own), UPDATE (customer + merchant),
        DELETE (cancelled only)
   Status values: pending, awaiting_shipment, shipped, delivered, completed, disputed, refunded, cancelled
   Escrow values: held, released, refunded

5. order_events
   Columns: id (uuid PK), order_id, event_type, previous_status, new_status,
            title, description, actor_type, metadata (jsonb), created_at
   RLS: INSERT (true), SELECT (customer via orders join)

6. order_tracking
   Columns: id (uuid PK), order_id (FK→orders, unique), merchant_id (FK→merchants),
            tracking_number, courier_partner, status, shipment_date,
            estimated_delivery, actual_delivery, notes, created_at, updated_at
   RLS: SELECT (customer via orders + merchant own), INSERT/UPDATE (merchant own)

7. tracking_updates

D. AUTHENTICATION
------------------
Provider: Custom phone+password (NOT Supabase Auth)
Session: Custom token-based (user_sessions table)
Role Mapping: user_roles table with app_role enum
Security Gaps:

  - CORS allows * (all origins)
  - profiles table RLS is too permissive (SELECT/UPDATE use "true")
  - password_hash potentially readable via anon key
